## Interpretation guardrails

The separate actual-agent arm exercised **one initial query worker, not twelve**: three serial useful explore calls, with actual retirement, subsequent empty pool and same-engine/session/generation reheat through a new reader/worker. That worker later retired too. Five-sample PB medians around the first exit were 232.7578→137.3828 MiB; around the later actual coordinator/writer closure, 120.3984→119.9180 MiB. These reinforce owner/lifetime relevance, not exclusive worker bytes or per-handle occupied caches. Actual-agent quiet 35–600 s engine PB median 120.37 MiB and late first-quiet 119.89 MiB do not explain a native allocator category. The later 60 s post-reheat median 174.48 MiB is unequally aged/stateful, not the same equilibrium, a leak result or an agent-versus-burst saving. Existing parser/resolver/extraction mechanisms remain unassigned; source-based candidates do not become measured causes merely because engine totals changed.

- Name the observed owner/lifetime before naming a category. Mark unassigned owners and unexercised paths explicitly.
- Report private commitment, private WS and total WS separately. Do not add isolate RSS values, V8 heap fields or overlapping external/ArrayBuffer values into a native total.
- An ended owner, a returned close method, reclaimed live allocations and reduced residency are different facts.
- Do not jump from native-private minus JS heap to SQLite, from multiple facade objects to full graph duplication, from elapsed idle time to actual retirement, or from a canary to an accepted primary/agent result.
- Bounded negative findings can rule out an explanation without selecting a different optimization. Return any remaining material allocator/retainer question to the later decision.
